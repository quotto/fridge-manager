# 横断品質・リリース作業計画案

## 1. 計画の位置づけ

本書は `docs/requirements.md` のうち、品質保証、AI 品質評価、セキュリティ／プライバシー、IaC／CI/CD、互換性検証、公開および運用を GitHub Issue 化するための分解案である。Epic は進捗集約用、Story／Enabler は原則として 1〜3 日で完了できる実行単位とする。

### 共通の完了条件

- 成果物、検証結果、未解決リスクが Issue またはリポジトリ内文書に記録されている。
- 自動化可能な受け入れ条件は CI で再現可能になっている。
- セキュリティ、プライバシー、AI 品質に関わる変更は `reviewer` の独立レビューを通過している。
- 実装変更は単体テスト、統合テスト、静的解析を通過し、必要に応じて E2E／実機検証を通過している。

### 担当ロール

| ロール | 主な責務 |
| --- | --- |
| `manager` | 依存関係・優先順位・受け入れ判定、Epic の進捗集約 |
| `developer-android` | Android アプリ、端末試験、アクセシビリティ、E2E |
| `developer-backend` | API、AI 連携、レート制御、監視機能 |
| `ai-evaluator` | 評価データ、評価基盤、モデル比較、回帰評価 |
| `reviewer` | 品質・セキュリティ・プライバシーの独立レビュー |
| `devops` | IaC、CI/CD、環境構築、監視、リリース運用 |

## 2. Epic Q1: 自動テスト基盤と横断品質ゲート

**目的:** Android、API、IaC を一貫して検証し、主要な受け入れ条件をリリースごとに再現できる品質ゲートを整備する。

**受け入れ条件:** Q1 配下の全 Issue が完了し、必須 CI が成功しなければ main へ統合できず、主要ユーザーフローの E2E 結果を追跡できる。

**依存関係:** なし（各実行 Issue は対象機能の実装 Epic にも依存する）  
**優先度:** P0  
**見積り:** Epic（子 Issue 合計）  
**担当:** `manager`（統括）、`developer-android`、`developer-backend`、`devops`、`reviewer`

**主要タスク:**

**担当:** `developer-backend`

**担当:** `developer-android`

**見積り:** M

## 3. Epic Q2: AI 品質評価とモデル採用判定

**目的:** 日本の家庭内食品に対するモデル品質、遅延、原価、保持要件を定量評価し、本番モデルとフォールバック方針を決定する。

**受け入れ条件:** 300枚以上の固定評価セットと再実行可能な評価基盤があり、NFR-010 の全指標・閾値および保持要件に基づく採用記録が承認される。

**依存関係:** AI API／プロンプトの評価可能な縦切り実装  
**優先度:** P0  
**見積り:** Epic（子 Issue 合計）  
**担当:** `manager`（統括）、`ai-evaluator`、`developer-backend`、`reviewer`

**目的:** 日本の食習慣と実利用条件を偏りなく評価できるサンプリング仕様を作る。

- [ ] 冷蔵庫全景、棚、買い物品、包装／裸、透明／不透明、重なり、暗所の構成比を決める
- [ ] 日本固有食材と21単位を網羅する割付表を作る
- [ ] 個人情報・人物・住所等の映り込み禁止、同意、保管、削除手順を定義する
- [ ] 学習用データと分離した固定評価セットの版管理方針を定義する

**受け入れ条件:** 300枚以上を満たすカテゴリ別割付、収集・除外基準、プライバシー手順がレビュー承認される。

## 4. Epic Q3: セキュリティ・プライバシー適合

**目的:** 認証、入力、画像、秘密、ログ、AI境界、利用者データの全ライフサイクルを保護し、日本国内公開に必要な説明責任を満たす。

**受け入れ条件:** 脅威モデルの高リスク対策、秘密・依存関係検査、保持なし検証、削除導線、公開文書とデータセーフティ申告が独立レビューを通過する。

**依存関係:** アーキテクチャとデータフローの確定  
**優先度:** P0  
**見積り:** Epic（子 Issue 合計）  
**担当:** `reviewer`（統括）、`developer-android`、`developer-backend`、`devops`

### Q3-1 Enabler: 脅威モデルとデータフロー図を作成する

**目的:** 端末、Firebase、AWS、Bedrock、ログ、公開Webページを横断して資産・境界・脅威を特定する。

**主要タスク:**

- [ ] 匿名ID、トークン、画像、AI結果、ローカル在庫、運用ログの流れを図示する
- [ ] なりすまし、リプレイ、DoS、画像爆弾、prompt injection、ログ漏洩を分析する
- [ ] データ保持場所・処理国・削除契機を一覧化する
- [ ] リスク、対策、検証Issue、残余リスクの台帳を作る

**受け入れ条件:** 全信頼境界とNFR-004/005のデータが網羅され、高リスクに担当・期限付き対策がある。  
**依存関係:** Epic Q3  
**優先度:** P0  
**見積り:** M  
**担当:** `reviewer`

### Q3-2 Story: 認証・App Check・リプレイ防止をセキュリティ検証する

**目的:** 正規アプリの有効な利用者だけが高額なAI APIを呼べることを確認する。

**主要タスク:**

- [ ] ID tokenの署名、期限、issuer、audience検証を試験する
- [ ] App Check／Play Integrityとlimited-use token消費を試験する
- [ ] 欠落、改ざん、期限切れ、再送、並行リクエストを試験する
- [ ] エラー応答やログからトークン・識別子が漏れないことを確認する

**受け入れ条件:** 無効・再利用トークンでBedrockが呼ばれず、正規リクエストのみが追跡可能なID付きで処理される。  
**依存関係:** Q3-1、認証/API実装、Q1-3  
**優先度:** P0  
**見積り:** M  
**担当:** `reviewer`

### Q3-3 Enabler: Bedrock保持なし・リージョン制約をデプロイゲート化する

**目的:** 画像が保持対象モデルやJP Geo外へ誤送信される構成を防ぐ。

**主要タスク:**

- [ ] モデルID、JP inference profile、Global profile不使用をIaC／設定で制約する
- [ ] 起動・デプロイ時に`allowed_modes`へ`none`があることを検証する
- [ ] 検証失敗時にBedrockを呼ばず安全停止する統合テストを追加する
- [ ] モデル呼び出しログ、S3 URI、プロンプト保存が無効であることを監査する

**受け入れ条件:** 保持なしまたはJP制約を満たさない設定がデプロイで失敗し、実行時も画像送信前に遮断される。  
**依存関係:** Q3-1、AWS IaC基盤  
**優先度:** P0  
**見積り:** M  
**担当:** `devops`

### Q3-4 Story: 画像入力・一時データ・ログの漏洩耐性を検証する

**目的:** 悪意ある画像と失敗経路を含め、画像・メタデータ・在庫情報が残存／漏洩しないことを確認する。

**主要タスク:**

- [ ] magic bytes不一致、破損、巨大寸法、40MP超過、圧縮爆弾相当を試験する
- [ ] EXIF除去、向き反映、変換後プレビュー、メモリ安全性を試験する
- [ ] 成功・失敗・キャンセル・クラッシュ後の一時ファイル削除を検査する
- [ ] CloudWatch／アプリログに画像、token、在庫一覧、直接識別子がないことを検査する

**受け入れ条件:** 不正画像はモデル呼び出し前に拒否され、全終了経路で規定時間内に削除され、機密情報をログから復元できない。  
**依存関係:** Q3-1、画像前処理/API実装、Q1-2、Q1-3  
**優先度:** P0  
**見積り:** M  
**担当:** `reviewer`

**目的:** 認証情報の混入とサプライチェーン／権限過多リスクを継続的に検出する。

## 8. GitHub登録時の補足

- 各Epic Issueの本文に子Issue一覧をチェックリストで持たせ、ProjectではEpic自体ではなく子Issueの状態を追跡する。
- 子Issueには本書のIDをタイトル接頭辞として付け、`type:story`／`type:enabler`、`priority:P0`等、`estimate:S`等、担当ロールのラベルを設定する。
- 依存関係はGitHubのblocked by／blocking関係または本文のIssueリンクで表現する。
- Q2の評価画像は一般のGit履歴や公開CI成果物へ格納せず、アクセス制御された保管先とハッシュ付き台帳のみをIssueから参照する。
- 人手アノテーション、法務確認、Play Console所有者操作などAIエージェントだけで完結しない作業は、人間担当者を追加アサインする。
