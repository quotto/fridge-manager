# Android アプリ実装 Issue 計画案

## 1. 計画方針

- 対象: `docs/requirements.md` のうち Android クライアントに関する FR-001〜FR-013、NFR-001〜NFR-010、AC-001〜AC-011。
- GitHub では本書の Epic と Story/Enabler をそれぞれ Issue として作成し、Story/Enabler は親 Epic を依存関係に持たせる。
- Story/Enabler は原則 1〜3 日（S〜M）で完了できる粒度とする。Epic の見積りは配下 Issue の総量を表す。
- 実装は Kotlin、Jetpack Compose、単方向データフロー、Coroutine/Flow を基本とする。ローカル永続化には Room を用いる想定とする。
- 各実装 Story はテストを同じ Issue の完了条件に含め、独立したレビューを経て Done とする。
- AWS API の実装そのもの、Bedrock モデル評価、AWS インフラ、公開 Web ページ、Google Play 公開作業は別担当計画の対象とする。本書では Android 側の契約・連携・表示までを扱う。

## 2. 担当チーム

| ai-agent ロール | 主担当 |
| --- | --- |
| `android-foundation-agent` | Gradle、Compose 基盤、アーキテクチャ、共通コンポーネント |
| `android-data-agent` | ドメインルール、Room、Repository、トランザクション |
| `android-media-agent` | Camera、Photo Picker、画像検証・変換、一時ファイル管理 |
| `android-auth-network-agent` | Firebase匿名認証、App Check、AWS APIクライアント、状態・エラー処理 |
| `android-ui-agent` | 在庫 CRUD、AI候補確認、設定画面、アクセシビリティ |
| `android-qa-agent` | 端末世代互換、性能、アクセシビリティ、E2E・リリース検証 |
| `reviewer-agent` | コード・セキュリティ・プライバシーの独立レビュー |

## Epic A: Android アプリ基盤と共通設計を構築する

**種類:** Epic  
**目的:** Android 11〜17で動作し、機能ごとの並行開発とテストを安全に進められる Kotlin/Compose アプリ基盤を確立する。  
**優先度:** P0  
**見積り:** L  
**担当:** `android-foundation-agent`

### 主要タスク

- [ ] Kotlin/Compose プロジェクトとビルド設定を用意する
- [ ] レイヤー境界、依存方向、ナビゲーション、状態管理を定義する
- [ ] 日本語表示、明暗テーマ、共通エラー表示の基盤を用意する
- [ ] Unit/Instrumented/Compose UI テストをCIから実行可能にする

### 受け入れ条件

- `minSdk 30`、`compileSdk 37`、`targetSdk 37` でビルドできる。
- Androidアプリ、ドメイン、データ、外部連携の責務と依存方向がコード上で分離されている。
- Debug ビルドとテストがローカルおよびCIで再現可能である。
- 秘密情報やAWS認証情報をアプリへ埋め込まない構成になっている。

### 依存関係

- 要件定義書の確定

## 3. 推奨実施順序

1. Epic Aの基盤を完了する。
2. Epic Bのドメイン/DBとEpic Cの画像取得を並行開始する。
3. バックエンドAPI契約と並行してEpic Dの認証・通信を構築する。
4. Epic B・Dの成果を統合してEpic Eの候補確認/一括確定を実装する。
5. 各Epicで継続テストを行いつつ、Epic Fで対象OS・非機能・アクセシビリティ・セキュリティのリリースゲートを完了する。

## 4. GitHub Projectへの配置案

- Epic Issue: `type:epic`、配下Issue: `type:story` または `type:enabler`。
- 全Issueに `priority:P0`〜`priority:P3`、`estimate:XS`〜`estimate:XL`、`area:android` を付与する。
- 作成直後は全Issueを `Backlog` に置き、依存解消・受け入れ条件明確化済みのものだけを `Sprint Ready` へ移す。
- 同時進行はDB境界、画像一時ファイル、API契約など共有領域の競合を避け、manager agentが統合順を管理する。
- Story/EnablerのPRは、実装担当以外の `reviewer-agent` が受け入れ条件とテスト結果を確認して `Review` から `Done` へ移す。
