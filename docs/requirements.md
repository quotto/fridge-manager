# 食材在庫管理 Android アプリ 要件定義書

## 1. 目的

家庭内にある食材の種類、在庫数、単位を Android 端末上で管理し、日常的な在庫確認と更新を簡単にする。手入力に加えて、カメラまたは端末内の画像をクラウド AI で解析し、登録・更新候補を自動入力することで、入力の手間を減らす。

AI の解析結果は必ず候補として扱い、ユーザーが内容を確認して確定するまで在庫には反映しない。

## 2. 対象範囲

### 2.1 対象に含むもの

- 食材在庫の一覧表示、登録、編集、数量更新、削除
- 食材名による登録済み食材のサジェスト
- 1 回につき最大 30 品目の一括登録・更新
- 端末カメラで撮影した画像、または端末内で選択した画像の AI 解析
- AI 解析結果の確認・修正・確定
- アプリ利用開始時の匿名ユーザー識別
- 食材データの端末内保存
- AI 解析に必要な AWS 上の API および AI 基盤との連携

### 2.2 初期リリースの対象外

- メールアドレス、電話番号、SNS アカウント等を使用した会員登録・ログイン
- 複数端末間での在庫データ同期
- 家族・グループ間での在庫共有
- 食材データのクラウド保存、バックアップ、復元
- 賞味期限、購入日、保管場所、価格、カテゴリ、メモ等の管理
- バーコード・レシートの読み取り
- 献立提案、買い物リスト、通知
- iOS、Web、タブレット専用 UI
- AI による解析結果の自動確定

## 3. 用語定義

| 用語 | 定義 |
| --- | --- |
| 食材 | 在庫管理の対象となる品目。食材名によって識別する。 |
| 在庫数 | 食材の保有量を 0 以上 100 以下で表した数値。 |
| 単位 | 在庫数の量を表す、アプリでプリセットされた選択肢。 |
| 差分更新 | 現在の在庫数に増減量を加算または減算する更新方法。 |
| 置換更新 | 現在の在庫数を、新たに入力・推定した在庫数で置き換える更新方法。 |
| AI 解析候補 | 画像から推定された食材名、在庫数、単位等の未確定データ。 |
| 匿名ユーザー ID | 個人情報によるログインを行わず、アプリ利用者を識別するために Firebase から付与される ID。 |

## 4. 利用者と利用条件

- 主な利用者は、自宅の食材在庫を自身の Android 端末で管理する個人とする。
- 利用者は認証画面やアカウント登録なしで利用を開始できるものとする。
- 手動による在庫管理はオフラインでも利用可能とする。
- AI 画像解析にはインターネット接続が必要とする。
- 初期リリースで提供する表示言語は日本語とする。

## 5. 業務ルール

### 5.1 食材の一意性

- 食材は食材名ごとに一意とし、同一名の食材を複数登録できない。
- 食材名は 1 文字以上 30 文字以下とする。
- 同一名判定では、入力値の前後空白を除去し、Unicode 正規化を行った文字列を比較する。
- 初期リリースでは、上記正規化後の文字列が完全一致する場合を同一名とする。表記揺れや類義語（例: 「玉ねぎ」と「タマネギ」）は同一視しない。
- 食材名の編集によって別の登録済み食材と同一名になる場合、更新を拒否して対象食材を案内する。

### 5.2 在庫数

- 在庫数は 0 以上 100 以下とする。
- 整数に加えて、小数を必要とする単位を扱えるものとする。
- 小数部は最大 2 桁とする。
- 差分更新の結果が 0 未満または 100 を超える場合は確定できない。
- 在庫数 0 の食材は削除せず、在庫切れとして保持できる。

### 5.3 単位

- 単位は自由入力ではなく、アプリ内のプリセットから選択する。
- 初期プリセットは次の 21 種類とする。
  - 重量・容量: 「g」「kg」「ml」「L」
  - 汎用・包装: 「個」「本」「枚」「袋」「パック」「箱」「缶」「瓶」
  - 日本の食材で一般的な数え方: 「束」「株」「玉」「丁」「尾」「切れ」「房」「合」「食」
- 「丁」は豆腐、「尾」「切れ」は魚、「房」はバナナやぶどう、「束」「株」「玉」は野菜、「合」は米、「食」は麺類や個包装食品等の管理を主な用途とする。
- 重量・容量を AI が推定する場合、同じ量を表す単位のうち在庫数が 0〜100 に収まる単位へ正規化する。100 g/ml 以下は g/ml を優先し、100 g/ml を超える場合は kg/L を使用する（例: 500 g は 0.5 kg、500 ml は 0.5 L）。
- 単位の変更時に在庫数の自動換算は行わない。ユーザーが変更後の在庫数を確認して確定する。

### 5.4 一括処理

- 1 回の登録・更新操作で確定できる品目数は最大 30 件とする。
- 1 つの画像に 30 件を超える食材が推定された場合、最大 30 件までを候補として表示し、上限超過をユーザーに通知する。
- 一括処理内に同一名の候補が複数ある場合、重複状態を表示し、ユーザーが統合または修正するまで確定できない。
- 一括処理では、各品目を個別に除外、修正できるものとする。
- 確定時は、検証を通過した全品目を一括して保存する。1 件でも不正な品目がある場合は保存せず、該当箇所を表示する。

## 6. 機能要件

### FR-001 在庫一覧表示

- アプリ起動後、登録済み食材の食材名、在庫数、単位を一覧表示する。
- 在庫数が 0 の食材は、在庫切れであることを識別できる表示にする。
- 食材が 0 件の場合は、手動登録または画像からの登録を開始できる空状態を表示する。
- 一覧の表示順は食材名の昇順を既定とする。

### FR-002 手動による食材登録

- ユーザーは、食材名、在庫数、単位を入力して食材を登録できる。
- 食材名、在庫数、単位は必須とする。
- 在庫数および単位は「5. 業務ルール」に従って検証する。
- 同一名の登録済み食材が存在する場合、新規登録は行わず、既存食材をサジェストする。
- ユーザーがサジェストを選択した場合、既存食材の更新操作へ切り替える。
- ユーザーがサジェストを選択しない場合でも、同一名のまま新規登録を確定することはできない。

### FR-003 食材名のサジェスト

- 食材名の入力中、登録済み食材から一致する候補を表示する。
- 候補には少なくとも食材名、現在の在庫数、単位を表示する。
- 完全一致する候補を、部分一致する候補より優先して表示する。
- サジェストは端末内の食材データを使用し、ネットワーク接続を必要としない。

### FR-004 登録済み食材の編集

- ユーザーは登録済み食材の食材名、在庫数、単位を編集できる。
- 編集内容はユーザーが確定するまで保存しない。
- 編集後の値は「5. 業務ルール」に従って検証する。

### FR-005 在庫数の更新

- ユーザーは、登録済み食材の在庫数を差分更新または置換更新できる。
- 差分更新では、増加または減少の別と差分量を指定する。
- 置換更新では、置換後の在庫数を指定する。
- 更新前に、現在値、更新内容、更新後の値を確認できるものとする。

### FR-006 食材削除

- ユーザーは登録済み食材を削除できる。
- 誤操作防止のため、削除前に対象食材名を示した確認を行う。
- 削除確定後は端末内の食材データから削除する。
- 初期リリースでは削除の取り消し・復元機能を提供しない。

### FR-007 画像入力

- ユーザーは、端末カメラで新たに写真を撮影するか、端末内の画像を選択できる。
- 画像送信前に対象画像をプレビューし、送信または選び直しができる。
- 入力形式は JPEG、PNG、WebP とし、アプリは送信前に RGB JPEG へ正規化する。アニメーション画像は対象外とする。
- 1 回の解析で送信できる画像は 1 枚とする。
- 選択元画像は 20 MiB（20,971,520 bytes）以下かつデコード後 40 MP 以下とする。アプリはサブサンプリングを使用し、巨大な原画像をフルサイズでメモリ展開しない。
- AI へ送信する画像は、3 MiB（3,145,728 bytes）以下、長辺 2,048 px 以下、総画素数 4,000,000 以下とする。
- 短辺 480 px 未満の場合は認識精度が低下する可能性を警告するが、一律には拒否しない。
- アプリは EXIF の向きを画素へ反映し、アスペクト比を維持して縮小し、JPEG 品質 85 を基準に 3 MiB 以下へ圧縮する。3 MiB を超える場合は品質 80、75 の順に再エンコードし、それでも超える場合は寸法を段階的に縮小する。小さい画像は拡大しない。
- 位置情報、撮影日時、端末情報等の EXIF メタデータを送信前に除去する。
- プレビューには、変換前の原画像ではなく AI へ実際に送信する変換後画像を表示する。
- 端末内画像の選択には Android Photo Picker を使用し、`READ_MEDIA_IMAGES` 等の広範な写真アクセス権限を要求しない。
- カメラ機能に必要な権限は撮影開始時にのみ要求する。権限が拒否された場合は理由と設定変更方法を案内し、画像選択と手動入力は引き続き利用可能とする。
- 変換または送信に使用した一時ファイルは、完了、失敗、キャンセルのいずれの場合も削除する。

### FR-008 AI による新規登録候補の生成

- AI は画像に含まれる食材を識別し、食材ごとに食材名、在庫数、単位の候補を返す。
- AI 解析候補は最大 30 品目とする。
- アプリは候補を編集可能な確認画面に表示する。
- 登録済みの同一名食材が候補に含まれる場合、その旨と現在の在庫を表示し、新規登録ではなく更新候補として扱う。
- AI が値を推定できない項目は未入力として示し、ユーザーに入力を求める。
- ユーザーは候補を追加、修正、除外してから確定できる。
- ユーザーが確定するまで、AI 解析候補を在庫データへ反映しない。

### FR-009 AI による在庫更新候補の生成

- ユーザーは登録済み食材の更新時に、1 枚の画像から食材ごとの数量の絶対値を候補として生成できる。
- AI は推定した絶対値が在庫の増加量、減少量、または置換後の在庫数のいずれであるかを決定しない。
- ユーザーは確定前に、AI が推定した絶対値の適用方法を「増加」「減少」「置換」から品目ごとに選択する。
- 「増加」を選択した場合、AI の推定値を現在の在庫数に加算する。
- 「減少」を選択した場合、AI の推定値を現在の在庫数から減算する。
- 「置換」を選択した場合、AI の推定値を更新後の在庫数として現在値と置き換える。
- 更新後の在庫数が範囲外になる場合は確定できず、修正を求める。
- AI の推定値、適用方法、更新後の値はすべてユーザーが確認でき、推定値と適用方法は確定前に修正できる。

### FR-010 AI 解析の状態・エラー表示

- 画像のアップロード中および AI 解析中であることを表示する。
- 解析成功時は候補を表示し、ユーザーの確認操作へ進む。
- タイムアウト、通信失敗、サービス障害、非対応画像、解析不能を区別可能なメッセージで通知する。
- 失敗時は在庫データを変更せず、再試行、画像の選び直し、手動入力を選べるものとする。
- 利用回数上限に達した場合は、上限の種別と再利用可能になる日時を表示し、手動入力へ移行できるものとする。
- 同一リクエストの再送によって在庫が重複更新されないものとする。

### FR-011 匿名ユーザー識別

- 初回起動時に Firebase Authentication の匿名認証を利用して匿名ユーザー ID を取得する。
- ユーザーにログイン操作を要求しない。
- 取得した ID は、AWS 上の AI 解析 API を呼び出す利用者の識別および不正利用抑止に使用する。
- Firebase の ID トークンを AWS 側で検証し、検証できないリクエストは AI 解析を実行しない。
- Firebase App Check と Play Integrity により正規アプリからの呼び出しであることを検証する。高額な AI 呼び出しには limited-use token のリプレイ保護を使用する。
- 匿名ユーザー ID を食材データのクラウド保存や端末間同期には使用しない。
- 匿名認証を一時的に開始できない場合でも、端末内の手動在庫管理は利用可能とし、AI 解析のみ利用不可とする。

### FR-012 ローカルデータ保存

- 食材データはアプリ専用の端末内ストレージに永続化する。
- 食材データを AWS、Firebase その他のクラウドサービスへ保存しない。
- アプリ再起動後も登録済み食材を利用できる。
- アプリのデータ消去またはアンインストールにより食材データが失われることを、利用者が認識できるよう案内する。
- 初期リリースではバックアップおよび復元を提供しない。

### FR-013 利用データの削除

- 設定画面から、端末内の全食材データおよび Firebase の匿名ユーザーを削除できる。
- 削除前に、復元できないことを明示して確認する。
- Firebase 匿名ユーザーが Google Play の「アプリアカウント」に該当するかを公開前に確認する。該当する場合は、本人性を確認できる削除用トークン等を用いてアプリ外からも削除を依頼できる公開 Web ページを提供する。
- 「アプリアカウント」に該当しない場合も、データの種類、保持期間、削除方法を説明する公開 Web ページを提供する。
- 不正利用防止等の正当な理由で削除後も保持する最小限のログがある場合は、その内容と保持期間をプライバシーポリシーに明記する。

## 7. データ要件

### 7.1 食材データ

| 項目 | 必須 | 内容・制約 |
| --- | --- | --- |
| 食材 ID | 必須 | 端末内で一意の、表示用途に依存しない識別子 |
| 食材名 | 必須 | 前後空白除去後 1〜30 文字。同一名を重複登録不可 |
| 正規化食材名 | 必須 | 同一名判定に使用する Unicode 正規化済み文字列 |
| 在庫数 | 必須 | 0 以上 100 以下、小数部最大 2 桁 |
| 単位 | 必須 | プリセット内の値 |
| 作成日時 | 必須 | 端末内でのレコード作成日時 |
| 更新日時 | 必須 | 端末内での最終更新日時 |

### 7.2 AI 解析リクエスト

- リクエストは、認証情報、リクエスト ID、処理種別、画像、および解析に必要な最小限の情報で構成する。
- 食材の更新候補生成に現在値が必要な場合は、対象品目の食材名、在庫数、単位のみを送信する。
- 端末内の全在庫一覧を一律に送信しない。

### 7.3 AI 解析レスポンス

- レスポンスは、リクエスト ID、解析結果、食材ごとの候補、警告、エラー情報を機械的に検証可能な形式で返す。
- 食材候補には、食材名、推定数量、推定単位、推定根拠、要確認フラグを含める。
- 推定根拠は「可視個数」「包装表示」「視覚推定」「不明」のいずれかとする。
- 個数は画像内で確認できる対象を数え、包装品は画像から読み取れる内容量を候補とする。液体・ばら物は、容器容量と充填率の双方を合理的に確認できる場合に限り数量を推定する。
- 数量を合理的に推定できない場合は 0 を補完せず「不明」とし、ユーザー入力を要求する。
- AI の確信度はフォールバック判定等の内部処理にのみ使用し、精度保証を示す数値としてユーザーへ提示しない。
- AI 出力は信頼できない入力として扱い、アプリおよび API の双方で型、文字数、数値範囲、件数を検証する。

## 8. 外部システム要件

### 8.1 Firebase

- Firebase Authentication の匿名認証を使用する。
- AWS 側は Firebase が発行した ID トークンの署名、有効期限、発行者、対象プロジェクトを検証する。
- Firebase App Check の Play Integrity プロバイダーを使用し、AWS 側で App Check token を検証する。
- Firebase に食材データおよび解析画像を保存しない。

### 8.2 AWS

- AI 解析 API、認証トークン検証後のアクセス制御、AI 基盤呼び出し、監視に必要なリソースを AWS 上に構築する。
- AI 基盤には Amazon Bedrock を使用し、第一候補モデルを Amazon Nova 2 Lite（JP Geo）とする。NFR-010 の比較評価に合格した時点で本番採用を確定する。
- AWS の処理リージョンは東京（`ap-northeast-1`）を起点とし、`jp.amazon.nova-2-lite-v1:0` により東京・大阪の JP Geo 内に限定する。Global inference profile は使用しない。
- Bedrock のデータ保持モードは `none` とし、起動時およびデプロイ時に対象モデルの `allowed_modes` に `none` が含まれることを検証する。条件を満たさない場合はモデルを呼び出さず、手動入力へ移行する。
- Bedrock Converse API の `toolChoice` で特定 tool を強制し、tool input schema の対応範囲内で最大 30 品目の構造化結果を取得する。Nova 2 Lite が対応していない Bedrock Structured Outputs 機能には依存しない。
- サーバーは tool input を JSON Schema で再検証し、不適合時は 1 回だけ再試行する。再試行後も不適合の場合はフォールバックまたは手動入力へ移行する。
- 推論設定は temperature 0 を基本とし、単純な抽出処理では reasoning を無効化する。最大出力トークン数は評価結果に基づき 1,500〜2,500 の範囲で設定する。
- Nova 2 Lite の再試行後も schema 不正、品目名・数量不明、遮蔽等が残る場合は Claude Sonnet 5 を品質フォールバック候補とする。ただし、使用環境で `data_retention_mode: none` が許可される場合に限る。
- Claude Sonnet 5 で保持なしを保証できない場合は、保持要件を満たす代替モデルまたはユーザーによる手動修正へ移行する。
- 画像はメモリ上の bytes として Bedrock へ直接送信し、S3 URI、モデル呼び出しログ、プロンプト保存を使用しない。
- CloudWatch にはリクエスト ID、モデル ID、レイテンシ、入出力トークン数、エラー種別のみを記録する。
- API はインターネットから直接 AI 基盤を無制限に呼び出せない構成とする。

## 9. 非機能要件

### NFR-001 対応環境

- Android スマートフォン向けネイティブアプリとする。
- アプリの実装言語は Kotlin とする。
- AWS 上の API および AI 連携処理の実装言語は TypeScript とする。
- 2026-07-16 時点の最新正式版 Android 17 から 6 世代前までを対象とし、Android 11〜17 をサポートする。
- `minSdk` は 30、`compileSdk` および `targetSdk` は 37 とする。Android 12L（API Level 32）も対応範囲に含む。

### NFR-002 性能・応答性

- 端末内の一覧表示、登録、更新、削除は、通常利用時に操作後 1 秒以内を目標に画面へ反映する。
- AI 解析は、通常時にリクエスト開始から 30 秒以内の完了を目標とする。
- AI 解析が 60 秒を超えた場合はタイムアウトとして扱い、再試行手段を提示する。
- 時間を要する処理中も画面を応答可能に保ち、処理状態を表示する。

### NFR-003 可用性・オフライン対応

- 端末内の閲覧および手動 CRUD は、AWS または Firebase の障害時やオフライン時にも利用可能とする。
- AI 解析機能が利用できない場合、その影響を AI 関連操作に限定する。
- AI 解析 API の目標稼働率は月間 99.0% 以上とする。ただし外部 AI サービスおよび Firebase の障害は別途計測する。

### NFR-004 セキュリティ

- 端末と Firebase、AWS 間の通信は TLS で暗号化する。
- AWS の認証情報、AI サービスの認証情報、秘密鍵をアプリ内へ埋め込まない。
- AI 解析 API は Firebase ID token と App Check token の双方を検証し、利用者単位および送信元単位でレート制限を行う。
- 画像の形式、実サイズ、宣言された Content-Type を検証し、許可された上限を超える画像を拒否する。
- サーバー側で magic bytes、JPEG デコード結果、幅、高さ、総画素数を再検証し、破損画像や展開後に異常に大きくなる画像を拒否する。
- ログに画像本体、Firebase ID トークン、秘密情報、端末内の在庫一覧を出力しない。
- AI から返された文字列を命令として実行せず、表示およびデータ候補としてのみ扱う。
- 外部依存ライブラリはサポート中の安定版を使用し、既知の重大な脆弱性がない状態を維持する。

### NFR-005 プライバシー・画像保持

- 画像は AI 解析の目的にのみ使用し、食材以外の被写体が含まれる可能性を送信前に案内する。
- クラウド側は解析完了または解析失敗後、処理に使用した画像を速やかに削除し、永続ストレージへ保存しない。
- 一時保存が必要な場合も処理中に限定し、遅くとも 1 時間以内に自動削除する。
- AI サービス事業者側のデータ保持条件がある場合は、画像がモデル学習に使用されない設定・契約を選択し、利用者向けプライバシー表示に明記する。
- 解析結果は API 応答として端末へ返し、クラウド側で継続保存しない。
- アプリの配布地域は日本国内に限定する。
- 個人情報保護法を前提に、画像に人物その他の個人に関する情報が映り込む可能性を考慮して、取得目的、送信先、保持期間、削除方法を明示する。
- Google Play とアプリ内の双方から参照可能な日本語のプライバシーポリシーを、公開された HTML ページとして提供する。
- プライバシーポリシーには、運営者・問い合わせ先、取得情報、利用目的、Firebase・AWS・AI モデル提供者への送信、保存場所、保持・削除方針、安全管理措置を記載する。
- Firebase Authentication が処理する匿名 ID、IP アドレス、User-Agent 等をデータ収集として扱い、Google Play のデータセーフティ申告を実態と一致させる。
- Firebase その他の委託先で国外処理が生じる場合は、送信先、所在国、利用目的および講じる保護措置をプライバシーポリシーに明記する。

### NFR-006 信頼性・整合性

- 端末内データの登録・一括更新はトランザクションとして処理し、部分的な保存を防ぐ。
- アプリまたは通信が中断しても、確定前の AI 候補が在庫へ反映されないものとする。
- API はリクエスト ID を用いて処理を追跡できるものとする。
- AI 出力が不正または要件外である場合は保存せず、ユーザーに修正または再試行を求める。

### NFR-007 ユーザビリティ・アクセシビリティ

- 主な操作は Android の標準的なナビゲーションと入力方法に従う。
- エラー時は原因と次に可能な操作を日本語で示す。
- 色だけに依存せず、テキストやアイコンを併用して状態を表す。
- 文字拡大、スクリーンリーダー、十分なタップ領域、明暗テーマを考慮する。
- AI 候補とユーザーが確定済みの在庫を視覚的に区別する。

### NFR-008 保守性・監視

- アプリ、API、AI 連携処理の責務を分離し、AI サービスを変更可能な境界を設ける。
- API のエラー率、レイテンシ、呼び出し数、AI 利用量、削除失敗を監視する。
- ログはリクエスト ID によって追跡可能とし、利用者を直接特定する情報を含めない。
- 画像の一時削除に失敗した場合は監視通知し、自動再試行または期限による削除を保証する。

### NFR-009 コスト

- 初期利用規模では、常時稼働サーバーを極力避け、従量課金型の構成を優先する。
- AI 解析は匿名ユーザー ID ごとに 5 回/日かつ 30 回/月、短時間は 2 回/分（burst 2）を上限とする。
- 日次・月次上限は日本標準時（JST）の暦日・暦月で集計し、日次は毎日 0:00、月次は毎月 1 日 0:00 にリセットする。
- AWS WAF で送信元 IP ごとに 10 回/分の防御的な上限を併用する。厳密なユーザー別上限はバックエンドの原子的カウンターで判定する。
- 全ユーザー合計 8,000 回/月を初期のハード上限とし、到達時は AI 解析のみを月初まで停止する。手動在庫管理は継続可能とする。
- AI 呼び出しを予約した時点で利用回数を計上し、入力不正や上限超過は計上しない。AI 基盤側の障害では予約した回数を戻す。
- AWS の月次予算上限を 50 USD とし、50% で通知、80% で緊急通知、100% で AI 解析停止を実行する。予算情報の更新遅延があるため、8,000 回/月の同期的な上限を主たる遮断手段とする。
- 上限値は設定で変更可能とし、利用実績、月間アクティブユーザー数、モデルの実測 p95 原価を基に定期的に見直す。
- AI モデルの選定では、食材・数量認識の品質、応答時間、画像保持条件、料金を評価する。

### NFR-010 AI 品質評価

- 本番採用前に、日本の家庭内食品を対象とする最低 300 枚の評価画像セットを作成する。
- 評価画像には、冷蔵庫全景、棚、買い物品、包装・裸の食材、透明・不透明容器、重なり、暗所、日本固有の食材、および全プリセット単位を含める。
- 正解データは 2 名が独立して付与し、不一致を調停する。
- 品目検出 F1、名称一致率、可視個数の完全一致率と平均絶対誤差、重量・容量の誤差、単位正解率、schema 適合率、要確認判定の再現率、p50/p95 レイテンシ、1 画像あたり原価を測定する。
- 初期受け入れ基準は、再試行後の schema 適合率 100%、単位正解率 95% 以上、可視個数の完全一致率 90% 以上、品目検出 F1 0.85 以上、存在しない品目の重大誤候補 1% 以下とする。
- 単眼画像から重量・体積を一意に特定できない場合があるため、その精度基準は PoC の実測後に定める。基準未達でも不明として適切にユーザー確認へ送れることを必須とする。
- モデルまたはプロンプト変更時は同じ評価セットで回帰評価を実施する。

## 10. 受け入れ条件

### AC-001 手動登録

- 有効な食材名、0〜100 の在庫数、プリセット単位を指定すると登録できる。
- 食材名は 30 文字まで登録でき、31 文字以上では登録できない。
- 無効な値または同一名の食材は登録できず、修正方法または既存食材が表示される。

### AC-002 更新・削除

- 登録済み食材の名称、在庫数、単位を変更でき、再起動後も変更が維持される。
- 差分更新と置換更新の双方で更新後の値を確認して確定できる。
- 削除確認を経て食材を削除でき、再起動後も削除状態が維持される。

### AC-003 一括処理

- 最大 30 品目を確認・修正して一括保存できる。
- 31 品目以上、不正値、または同一名の重複を含む状態では確定できない。
- 保存エラー時に一部の品目だけが反映されない。

### AC-004 AI 登録

- カメラ画像または端末内画像から食材候補を取得できる。
- AI が返した候補は確定前に編集・除外できる。
- ユーザーが確定しない限り、在庫データは変化しない。
- 登録済みの同一名食材は更新候補として表示される。

### AC-005 AI 更新

- 1 枚の画像から、食材ごとの数量の絶対値を取得できる。
- AI 推定値の適用方法を「増加」「減少」「置換」から選択でき、それぞれの方法に応じた更新後の値が表示される。
- 更新後の値が 0〜100 の範囲を外れる場合は確定できない。
- 通信失敗や解析不能時に在庫は変化せず、再試行または手動入力へ移行できる。

### AC-006 データ保管とプライバシー

- 食材データがクラウドへ保存されず、端末内操作はオフラインで利用できる。
- 解析画像および解析結果がクラウド上に継続保存されない。
- ログから画像、認証トークン、在庫一覧を復元できない。

### AC-007 匿名識別

- 初回起動時に利用者の入力なしで匿名 ID を取得できる。
- 有効な Firebase ID token および App Check token なしでは AI 解析 API を利用できない。
- 匿名認証または AI API が利用できない場合も、手動在庫管理を継続できる。

### AC-008 画像前処理

- JPEG、PNG、WebP を選択すると、向き補正とメタデータ除去を行った 3 MiB 以下、長辺 2,048 px 以下、4 MP 以下の JPEG に変換される。
- 20 MiB または 40 MP を超える原画像、不正形式、または変換後も送信上限を満たさない画像は送信されない。
- 短辺 480 px 未満の画像には精度低下の警告が表示される。
- 画像選択時に広範な写真アクセス権限を要求しない。

### AC-009 AI 利用上限

- 同一匿名ユーザーが 5 回/日、30 回/月、2 回/分のいずれかを超えると AI 解析が拒否され、再利用可能日時が表示される。
- 日次上限は JST の毎日 0:00、月次上限は JST の毎月 1 日 0:00 にリセットされる。
- 全体上限または予算上限により AI 解析を停止しても、端末内の閲覧と手動 CRUD は利用できる。

### AC-010 データ削除と国内配布

- ユーザーはアプリ内からローカル食材データと Firebase 匿名ユーザーを削除できる。
- Google Play のストア表示、データセーフティ申告、アプリ内表示から同一内容の日本語プライバシーポリシーを確認できる。
- Google Play 上の配布対象国は日本のみである。

### AC-011 対応環境・AI基盤

- Android 11、12、12L、13、14、15、16、17 の各環境で主要機能が正常に動作する。
- Bedrock の有効なデータ保持モードが `none` でない、または対象モデルの `allowed_modes` に `none` がない場合、画像をモデルへ送信せず手動入力へ移行する。
- 500 g、500 ml の AI 推定値はそれぞれ 0.5 kg、0.5 L として候補表示され、0〜100 の在庫数制約を満たす。

## 11. 前提として採用した判断

`draft.md` に明示されていない事項について、以下を前提として採用した。

- 「認証不要」と「Firebase による一意 ID 付与」を両立するため、Firebase Authentication の匿名認証を採用する。
- 食材名の表記揺れを自動統合すると誤統合の危険があるため、前後空白除去と Unicode 正規化後の完全一致のみを同一名とする。
- 重量や容量を扱えるよう在庫数は小数第 2 位まで許可する。
- 食材データをクラウド保存しないため、複数端末同期、バックアップ、アンインストール後の復元は初期リリースの対象外とする。
- AI 解析は 1 回 1 画像とし、候補を最大 30 品目に制限する。
- AI による在庫更新では 1 枚の画像から数量の絶対値のみを推定し、その適用方法はユーザーが「増加」「減少」「置換」から選択する。
- AI の誤認識を前提として、すべての候補にユーザー確認を必須とする。
- AI 利用上限と予算は初期利用規模を 500 MAU、通常利用を 1 ユーザーあたり月 8 回程度と仮定して設定し、実績に応じて見直す。

## 12. 制約

- Android アプリは Kotlin で実装する。
- クラウド側の API および AI 連携処理は TypeScript で実装する。
- クラウドリソースは原則 AWS 上に構築する。
- ユーザー識別には Firebase を使用する。
- 食材データはクラウドへ保存せず、端末内にのみ保存する。
- AI 解析に送信した画像は永続化しない。
- 機能・品質要件を満たす範囲で、低コストな構成を優先する。
